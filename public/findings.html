What the port experiments found so far

Thirteen candidate stacks, one test bench, forty-one promises. Four findings that matter for secure data storage, group spaces and delivery, with the evidence behind each.

The test bench runs the same scenarios against every candidate: group membership under conflict (S1 to S11), an adversarial carrier (T1 to T12) and, since this week, pair delivery (T9, T10, Z1 to Z5). A candidate is a stack behind a narrow driver interface. Results are promises per port, not scores: each cell says whether all scenarios mapped to a promise passed. Everything below is reproducible from the public repository, linked at the end.

Four findings

01

One authority log, two key protocols, the same promise row

We run our authority log (membership decided by a conflict matrix, signed entries, policy) over two group key protocols: BeeKEM, Keyhive's CGKA, and MLS (RFC 9420, OpenMLS 0.9.1). Both deliver an identical row in the matrix: 25 promises kept, 1 not kept, 5 not applicable, 10 untested. The one gap is the same in both: a blind carrier that freezes a device's feed is not detectable without an attested target.

What MLS needs from the layer above, because it is linear (one commit per epoch): a single healer per group, reconciliation after every commit, a welcome that carries the digest of its admitting commit, and re-sealing of frames whose epoch lost a tiebreak. A room model where the commit itself decides membership keeps fewer promises on the same bench (see the two MLS room rows in the summary below; the any-staged mode decides one scenario, S4f, by a hash tie-break, so its row can differ between runs). Candidates rltp-beekem, rltp-mls.

02

Without history there is no CRDT, not even for new entries

If a newcomer only receives keys from the epoch it joined, it cannot read earlier entries. That part is expected. What the bench showed in addition: the newcomer cannot integrate new entries either, because CRDT updates reference the entry before them. A second device of an existing member reads nothing at all.

For independent chat lines this never surfaces. For shared state (a map, a calendar, a board) a key chain across epochs is a precondition, not a comfort. Scenarios S5, S6, S6b on the model without history; the same scenarios pass with a predecessor table in every sealed frame.

03

Delivery semantics live in the adapter, not in the wire

We sent the same sealed envelope through four wires: our plain envelope, TSP Rev 3 and DIDComm v2 in authcrypt and anoncrypt mode. All four produce the same delivery behaviour: a sender status trias, at-least-once with receiver dedup, a pre-transport report when offline, carrier switch without losing the relationship. The wires differ only in what the carrier learns and where a foreign sender is rejected.

04

Portable Web Spaces carries a group as blind storage, with one gap

One space per group, one collection of sealed frames, reading over the per-device changes feed, the space controller is a group key. Every scenario passes as it does over our own relay, including the adversarial carrier scenarios and a server switch by export and import.

What the server learns: the space id; per resource the sender device id and the frame label as plaintext fields, a resource id made of that device id and a sequence number, size and timestamp; the addressee of welcomes. Content, person names and the group secrets stay sealed. A pseudonym per device and group would remove the device ids from the server; that is not built. The gap: a frozen feed is not detectable while the server issues no attested target. That is exactly the job a group controller profile would have. Load at 30 members, 100 operations: about 290 ms per operation, half of it HTTP. Candidate rltp-beekem-pws.

Two findings specific to MLS

  • A clone's commit locks out the original device. If a stolen device state commits, the real device cannot process that commit (OpenMLS accepts no message from its own leaf) and falls permanently behind the tree. The healer sees no reason to act. Something must detect "a commit from my own leaf that I did not make" and request a fresh welcome.
  • A stale stolen state can force rollbacks. With snapshots for the last eight epochs, a commit from an old epoch with a lower hash makes every member roll back, re-seal and heal. No access is gained, but the lever repeats. A possible rule: commits from leaves the log has removed never enter the tiebreak.

Welcome size, measured. With the ratchet tree in the welcome: 839 B at one member, 2.7 KB at ten, 6.5 KB at thirty, about 190 B per further member. A 16 KB message bound is reached around eighty members.

What we would like to work on with this group

  • A group controller profile for a space (with Portable Web Spaces): the controller key set is a quorum-signed authorization view, the server attests its stored frontier, members verify convergence against it. Our side of that is built and measured.
  • The comparison matrix on GitHub: we keep our own rows current and contribute scenarios.
  • Delivery over TSP and DIDComm: the four-wire bench is public; adding a real mediator or intermediary as a carrier is the next step.
